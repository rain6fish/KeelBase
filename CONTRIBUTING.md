## Getting Started

### Prerequisites

- **Flutter**: >= 3.0 (see [Flutter installation guide](https://flutter.dev/docs/get-started/install))
- **Dart**: bundled with Flutter
- **Node.js**: >= 22 (for Taro admin frontend)
- **PostgreSQL**: >= 14
- **Redis**: >= 6 (optional, for caching/queues)
- **Docker**: >= 20 (for local infrastructure)

### Local Setup

1. Fork the repository
2. Clone your fork:
   ```bash
   git clone https://github.com/rain6fish/KeelBase.git
   cd KeelBase
   ```
3. Install backend dependencies:
   ```bash
   cd Server-NestJS
   npm install
   ```
4. Install Flutter dependencies:
   ```bash
   cd ../Front-Flutter
   flutter pub get
   ```
5. Copy and configure environment variables:
   ```bash
   cp .env.example .env
   ```
6. Start infrastructure (PostgreSQL, Redis, etc.):
   ```bash
   docker compose up -d
   ```
7. Run migrations:
   ```bash
   npm run migration:run
   ```
8. Start the development server:
   ```bash
   npm run start:dev
   ```

## Development Workflow

### Branch Naming Convention

- `feat/<feature-name>` — new features
- `fix/<bug-name>` — bug fixes
- `docs/<topic>` — documentation changes
- `refactor/<module>` — code refactoring
- `test/<module>` — adding or updating tests
- `chore/<task>` — routine tasks (deps, CI, etc.)

### Commit Message Convention

We follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <description>

fix(auth): resolve token refresh race condition
docs(readme): update setup instructions
feat(ai): add RAG query endpoint
```

**Types**: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`

## Pull Request Process

1. **Fork and branch**: Create a new branch from `main`
2. **Code changes**: Write or update tests for your changes
3. **Lint and test**: Ensure all checks pass:
   ```bash
   npm run lint
   npm run test
   ```
4. **Submit PR**: Fill in the PR template with:
   - Description of changes
   - Related issue number
   - Screenshots (if UI changes)
   - Test coverage notes
5. **Review**: Wait for maintainer review. Address feedback promptly
6. **Merge**: Once approved, a maintainer will merge your PR

### PR Checklist

- [ ] Code follows project style guidelines
- [ ] Tests added/updated and passing
- [ ] Documentation updated (if applicable)
- [ ] No debug code or console.logs in production code
- [ ] Commit messages follow Conventional Commits

## AI-Generated Code Policy

This project recognizes that contributors may use AI-assisted tools (such as GitHub Copilot, ChatGPT, etc.) during development. To maintain code quality and legal compliance, the following rules apply:

### 1. Responsibility

- You are **fully responsible** for all code you submit, regardless of whether it was written by you, generated by AI, or modified from AI output.
- Before submitting, review and test all AI-generated code to ensure it:
  - Solves the stated problem correctly
  - Does not contain security vulnerabilities
  - Follows the project's coding standards
  - Does not reproduce copyrighted code from other projects

### 2. Attribution

- If a substantial portion of your contribution was generated or significantly assisted by AI, please add a comment at the top of the file or in the PR description noting the tool used (e.g., `// Generated with assistance from GitHub Copilot`).
- This is not a legal requirement but helps maintain transparency in the project's development history.

### 3. No Plagiarism

- AI tools should not be used to reproduce code from other open-source projects or proprietary codebases.
- If your AI-generated code is substantially similar to existing code in another project, you must:
  - Rewrite it to be original
  - Or properly attribute the source and ensure license compatibility

### 4. Security Review

- All PRs containing AI-assisted code will receive additional scrutiny for:
  - SQL injection or injection vulnerabilities
  - Hardcoded secrets or credentials
  - Unintended data exposure
  - License incompatibility

## Reporting Issues

> **🔐 Security vulnerabilities**: Please **do not** open a public issue. Follow the [SECURITY.md](./SECURITY.md) disclosure process — email the maintainer privately for a coordinated fix.
>
> **🔐 安全漏洞**：请**不要**提交公开 Issue。请遵循 [SECURITY.md](./SECURITY.md) 的披露流程，通过邮件私密联系维护者以协调修复。

### Before Creating an Issue

1. **Search existing issues** — make sure it hasn't been reported
2. **Check the documentation** — your question might already be answered
3. **Isolate the problem** — try to reproduce with minimal code

### Issue Templates

- **Bug Report**: Use the `bug_report` template. Include:
  - Steps to reproduce
  - Expected vs. actual behavior
  - Environment details (OS, Flutter/Dart version, Node version)
  - Screenshots or logs if applicable

- **Feature Request**: Use the `feature_request` template. Include:
  - Problem description
  - Proposed solution
  - Alternative solutions considered
  - Use case context
