# KeelBase AI 开发宪法

## 0. 宪法地位

本宪法是 KeelBase **一切开发工作的总纲**。它由三个既有 skill 整合优化而来：

- `keelbase-product-development`（产品篇）
- `keelbase-ux-experience`（体验篇）
- `keelbase-architecture-engineering`（架构与工程篇）

整合时对比了 Anthropic 官方 skill 体系（spec-driven / test-driven / code-review / security-review / system-design）与 mattpocock engineering skills（implement→to-spec→to-tickets→code-review 流程、完成定义），补齐了原三篇缺失的**开发生命周期流程**、**完成定义 DoD** 与**项目实际执行约定**，并去重了三篇之间重复的条目（北极星目标、双用户模型、单开发者约束、参考应用规则等，均只保留一份定义）。

**配套文档（按需查阅，不重复收录细则）**：

| 文档 | 内容 |
|------|------|
| `CLAUDE.md` | 技术栈、API 规范、安全规则、§5.5 产品架构红线、§9 端点汇总 |
| `AGENTS.md` | 新增业务模块的 7 处接线清单、预置 Skills 表 |
| `docs/*.spec.md` / `docs/adr/` | 各功能规格与架构决策记录 |
| 私有 roadmap | 未做项/后续项追踪 |

**适用与触发**：开发、设计、实现、评审、重构任何 KeelBase 相关代码或配置前，先读本宪法；对非平凡改动，必须先在答复中给出第 4.2 节的「开发前必答」评估，再动工。

**顶层决策规则**（所有两难场景的最终裁决，见 §5）：

> 最小改动创造真实用户价值，同时保住信任、兼容、可测、可私有部署——`真实客户价值 > 终端可用性 > Builder 可用性 > 业务安全 > PMF 证据 > 可复用性 > 技术优雅 > 功能广度`。

## 1. 产品篇（Product）

### 1.1 使命与承诺

KeelBase = **Enterprise AI Trust Runtime + AI 应用工程平台**。平台位于 AI Agent 与既有业务系统之间，**不替代** ERP/CRM/项目管理套件/通用 Agent 框架。

- 产品承诺：让开发者**快速且安全**地构建 AI 业务应用；让业务用户**安全、可审计、可控**地用应用完成真实工作。
- 主循环：`Build -> Run -> Trust -> Private Deploy`
- 生态循环：`Platform -> Reference Applications -> Customer Projects -> Real-world Feedback -> Better Platform`

### 1.2 双用户模型（强制）

每个功能必须为**两组用户**分别评估，绝不视为同一"用户"：

**A. Builder / Developer**（用 KeelBase 构建/集成/定制/治理/部署 AI 应用的人：企业开发、SaaS 开发、集成商、独立开发者、未来交付工程师）
- 任务：连接现有系统/定义业务模型 → 理解或创建 Application Protocol → 定义 AI 工具/Agent → 配置权限与治理 → 测试评估 → 部署维护
- 成功标准：易理解、易上手、易集成、易定制、易调试、易部署、**默认安全**

**B. End User / Business User**（使用 KeelBase 构建的应用完成业务工作的人：销售、项目经理、员工、审批人、业务经理；通常不需要知道 KeelBase 存在）
- 任务：完成任务、查信息、分析业务、让 AI 做有用的操作、审阅/确认重要操作、理解结果
- 成功标准：完成快、界面直觉、AI 行为可理解、高风险操作有明确确认、错误可恢复、业务概念可见而平台复杂度隐藏

**产品规则**：平台复杂度属于 Builder/Admin 体验，不属于终端体验。不得向普通业务用户暴露 MCP、CASL、Tool Registry、Protocol 内部、审计哈希链、Agent Runtime 内部等概念，除非确有业务需要。

### 1.3 八维产品评审

每个有意义的特性从八个维度过一遍：

1. **市场** — 对齐真实且增长的企业 AI 问题？
2. **客户** — 企业为何需要？消除什么痛点？
3. **Builder** — 让构建/集成/定制更容易？
4. **终端用户** — 让应用更有用/可用/可信？
5. **竞争** — 为何用 KeelBase 而非自建、Dify、LangChain、Agent 框架、AI 网关、其他治理产品？
6. **买家** — CTO/架构师/安全负责人/IT 负责人会批准采用？
7. **商业** — 支撑开源 + 方案交付 + 企业授权的可信未来模式？
8. **技术** — 可靠、可维护、安全、可测、与现有架构一致？

技术分高但客户/用户价值分低的特性，不因"技术上感兴趣"而优先。

### 1.4 特征决策框架（非平凡特性必答）

- 解决什么用户问题？
- 影响哪组用户：Builder / End User / Both？
- 具体的 Job To Be Done 是什么？
- 能证明价值的最小版本是什么？
- 如何改进 Build / Run / Trust / Private Deploy 之一？
- 能否在真实业务场景演示价值？
- 能否复用现有能力而非新增子系统？
- 是否强化 AI CRM / PM / Approval 参考应用？
- 能否成为可复用基础设施或方案模板？
- 可测量的验收标准是什么？
- **明确不做的是什么？**

答不清则先澄清产品需求，再编码。

### 1.5 北极星与 UX 目标

- **平台北极星**：`首次可信应用时长 <= 30 分钟`
- **应用北极星**：`成功的业务结果`（不唯对话数、token 数、功能数）

体验目标：理解 ≤60s / 首次运行 ≤10min / 首次价值 ≤10min / 首次 AI 业务动作 ≤15min / Builder 首次自定义工具 ≤30min。

外部开发者的理想流程：`现有系统/新需求 -> Protocol -> AI 应用 -> 治理 -> 部署`。

### 1.6 Golden Demo 原则

特性应强化**一条连贯的端到端业务流**，而非孤立技术演示。黄金路径：

`用户请求 -> AI 理解 -> 读业务数据 -> 工具调用 -> 权限校验 -> 确认 -> DB 副作用 -> 审计 -> 撤销`

特性使该路径更可靠、可理解、可复用、易构建，即有价值。

### 1.7 业务安全 Agent 规则

任何允许 AI 改变业务状态的特性必须保住信任链。有意义副作用的最低要求：

- 明确的工具边界
- 授权/权限校验
- 风险感知治理
- 需要时人工确认
- 适用处副作用幂等
- 可审计执行
- 技术适用处可恢复/可撤销
- 评测或回归覆盖

**绝不**以削弱业务安全换取自主执行。产品原则：`Agent 框架帮 AI 做事；KeelBase 帮企业敢于让 AI 做事。`

### 1.8 旗舰应用优先级

默认顺序：**AI CRM（P0 ⭐⭐⭐⭐⭐）→ AI Project（P1 ⭐⭐⭐⭐☆）→ AI Approval/Knowledge（P1/P2 ⭐⭐⭐☆☆）**。

- **CRM** 证明完整业务安全 Agent 闭环：`Query -> Analyze -> Risk -> Create Task -> Confirm -> Execute -> Audit`。MVP 偏客户/商机/跟进/任务/风险/AI 搜索分析/受控 AI 写操作/确认/审计/业务看板。
- **PM** 证明多实体协调：Project/Task/Milestone/Schedule/Risk/Member/Document。
- **Approval/Knowledge** 证明 Knowledge + Policy + Human-in-the-loop + Approval + Audit。

无真实用户证据前，不把旗舰扩成庞大企业套件。

### 1.9 产品架构红线（CLAUDE.md §5.5，必须遵守）

1. **只有三个入口**：主 App（Front-Flutter）/ 小程序（Front-Taro）/ Web 端宿主（Web-Admin-Vue，工作台+管理台同壳）。所有后台管理功能一律并入管理端，禁止在 App/小程序实现管理员 CRUD/权限/审计。
2. **管理页不出现用户隐私数据**；必须出现时掩码：`/users` 等服务端 `sanitizeForAdmin` 脱敏（email/phone 掩码，bio/生日/名姓/头像不返回）；审计 `requestBody` 敏感字段自动打码；主 App 本人路径可明文。
3. **管理端必须双语**（中/英，`src/i18n/`，跟随系统 + 顶部切换器），禁止硬编码中文。
4. **审计必须显示用户名 + 功能实际名称**：操作审计/AI 审计左联用户表带 `username`；功能名由 `feature-map.ts` 生成语义 key，前端按语言渲染。

### 1.10 反功能膨胀与市场怀疑

**不要**仅因"竞品有 / 演示好看 / AI 能快速实现 / 架构上很有趣 / 将来可能有用"就加功能。加之前问：`发布后客户行为或可测量产品结果会怎么变？` 无可信答案则推迟。默认"暂不做"：通用 Workflow Designer、GraphQL、语音、支付、大规模 SaaS 多租户、通用 BPM、API 网关、过多模型供应商扩展等。

始终包含反向问题：`客户为什么不用 KeelBase？`（自建 / 现有 Agent 框架 / Dify / 直接用 MCP / AI 网关治理产品 / 推迟 AI）。特性在增加"选 KeelBase 而非替代品"的理由时才是战略强的。

### 1.11 开源与交付

支撑两条互补成长路径：

`开源 -> 开发者采用 -> 参考应用 -> 客户项目`

`开源 -> 生产采用 -> 私有部署 -> 企业支持/授权`

PMF 证据出现前，**不提前**为 SaaS 多租户、计费、市场机制做产品优化。

### 1.12 产品语言纪律

首选表述：「AI 业务应用」「业务安全 Agent」「企业 AI Trust Runtime」「Application Protocol」「可信业务动作」「Builder」「业务用户」「参考应用」「方案模板」。避免将 KeelBase 定位成通用 Agent 框架、通用 CRM、通用低代码平台、通用 AI 聊天机器人。

## 2. 体验篇（UX）

> 双用户模型定义见 §1.2；北极星与时延目标见 §1.5，此处直接引用，不重复。

### 2.1 双体验

- **Builder UX**：`理解 -> 创建 -> 连接 -> 配置 -> 测试 -> 治理 -> 部署`。优化可发现性、可预测配置、低上手摩擦、Protocol/Tool/Agent/权限/治理/应用的清晰关系、有用校验、可行动错误、易调试、审计/评测反馈可见、模板复用、简单本地/私有部署。引入配置时先问：默认值能否消除配置？
- **End User UX**：应用应表现为**正常业务应用 + 有用的 AI 辅助**。优化熟悉导航、任务导向页面、清晰业务术语、明显 AI 入口、简洁 AI 结果、上下文动作、高风险操作可见确认、清晰成败状态、恢复/撤销、响应性能。不因内部存在就暴露平台概念。

### 2.2 核心 UX 原则

1. 业务价值先于平台复杂度
2. 首次成功先于高级可配置性
3. 渐进披露：只在需要时暴露复杂度
4. AI 动作默认安全
5. 系统状态清晰：用户知道 AI 在做什么、发生了什么、什么需要确认
6. 错误可行动、可恢复
7. 复用熟悉的企业交互模式，不发明多余隐喻
8. 不强迫终端用户理解 Agent/MCP/Protocol/CASL/Tool Registry/审计链/运行时内部
9. 每个重要 AI 动作都有可理解的业务结果
10. 偏好短而连贯的工作流，而非丰富但混乱的界面

### 2.3 AI 交互规则

AI 做业务工作时不应像不透明聊天机器人。

- **只读**：`用户意图 -> AI 理解 -> 取数 -> 结果 -> 需要时给来源/上下文`
- **副作用**：`用户意图 -> AI 理解 -> 提议动作 -> 风险/权限评估 -> 需要时人工确认 -> 执行 -> 结果 -> 审计`

**确认 UI 必须说清**：将要发生什么、影响哪个业务对象、重要后果、谁/什么在授权、如何取消。禁止只说「你确定吗？」的确认框。

### 2.4 接受状态

有意义的 UI 流显式覆盖：首用/引导、空态、加载、成功、部分成功、校验错误、权限拒绝、AI/工具失败、超时、需确认、已取消、重试、恢复/撤销。只做好快乐路径、失败路径混乱 = 不完整。

### 2.5 业务语言 vs 技术语言

安全必须可理解但不暴露实现。

- 好：`将为 3 个客户创建跟进任务，创建前请确认。`
- 坏：`CASL 策略 ToolPermission.CREATE_CUSTOMER_TASK 拒绝/允许。`

技术细节可进 Admin/开发者 trace，普通用户给业务语言解释。（对照本项目已落地的 businessLabel/errorLabel 业务语言化——见 `utils/businessLabel`。）

### 2.6 信息架构

- **Builder/Admin 导航**：Applications / Protocols / Agents / Tools / Governance / Policies / Audit / Evaluation / Deployment
- **End User 导航**：Customers / Opportunities / Activities / Tasks / Projects / Approvals / Documents / Knowledge / AI Assistant

不要镜像 Builder 导航进业务应用。

### 2.7 多端规则

不自动跨 Web / Flutter / Taro 复制每个功能。按任务选主交互面：Builder/工作台 Web 优先；业务操作按真实使用模式选 Web/移动；轻量现场任务有证据再上移动。多端一致的是概念与状态，不一定是相同屏幕。

### 2.8 UX 测量与盲测

可量化指标：首跑成功率、任务完成率、任务耗时、错误率、放弃率、首价值时长、AI 动作确认率、AI 业务动作成功率、重复使用、30 日留存、满意度/NPS。

重要发布做**盲测**：让不理解 KeelBase 的人完成——解释产品做什么 / 启动系统 / 完成一个有价值的 AI 业务任务 / 执行或审阅一次受治理业务动作 / 找到查看发生了什么的地方 / Builder 连接或创建一个自定义工具。记录犹豫、求助、失败、误解之处。

### 2.9 UX 反模式

避免：业务界面用开发术语；导航暴露全部内部能力；首价值前巨型配置表单；与真实业务动作脱节的 AI 聊天；无适当确认的破坏性 AI 动作；建议与执行界限不清；静默失败；通用技术错误；过量模态框；无证据跨渠道复制流程；只为截图/演示外观设计。

## 3. 架构与工程篇（Architecture & Engineering）

### 3.1 架构原则

不把项目变成零散子系统。核心链路：

`既有业务系统/新业务模型 -> Application Protocol -> AI 应用 -> 业务安全 Agent Runtime -> 治理 -> 审计 -> 私有部署`

优先扩展与复用现有能力，而非引入平行框架。工程决策优先级：正确性与业务安全 > 与现有架构兼容 > 可测与回归安全 > 运维可靠 > 可维护 > 开发体验 > 影响真实负载的性能 > 技术优雅。不因风格偏好重写稳定子系统。

### 3.2 现有能力复用清单（动工前先查是否已存在）

Application Protocol、AI Tool Calling、Memory/RAG/Skills/SubAgent、CASL 权限、工具级治理、写工具确认、副作用幂等、撤销/恢复、审计哈希链(HS-11)、AI Eval 基线循环、Agent 决策/行为 trace 或回放、MCP 网关、FLOW 编排、Plugin/Template、Web Admin Workbench、`keelbase init`、Docker/单容器/离线部署、本地 Ollama、Demo Seed/Live Demo、WebSocket/Webhook。**先验证仓库真实实现，再假定 API/模块存在。**

### 3.3 业务副作用安全

任何能改变业务状态的 AI 能力必须评估：授权、数据级权限、工具级策略、确认要求、幂等、审计日志、错误处理、适用处回滚/撤销、评测/回归测试。**绝不**为简化实现绕过既有治理。

### 3.4 Application Protocol 纪律

Protocol 是业务能力与 AI 应用生成/运行时之间的稳定契约。扩展时：语义显式、schema 对 AI 可读、尽量向后兼容、区分业务含义与实现细节、不嵌入供应商特定假设、生成的产物保持普通源码。不把 Protocol 变成替代一切 API 规范的私有品。

### 3.5 集成原则

连接而非替代既有系统。优先：现有数据模型、OpenAPI 集成、协议适配器、MCP、显式 API、事件/Webhook。避免重复企业系统数据或逻辑。

### 3.6 前后端边界

后端负责业务规则、权限、治理、AI 编排、持久化、权威状态迁移；前端负责展示、交互、本地 UI 状态、用户确认、清晰业务反馈。**不把安全决策移进纯客户端逻辑。**

### 3.7 测试要求

有意义的改动补对应层测试。至少考虑：单测、集成、AI/工具行为、权限、治理、审计、重要用户流 E2E、部署行为变化时的部署/冒烟。业务关键的 Agent 动作，**允许与拒绝两条路径都测**。

### 3.8 回归纪律

收尾前：识别受影响模块、查既有测试、先跑聚焦测试、风险高时跑更广回归、检查安全/治理行为、适用时验证生成代码/构建产物、涉及部署时验证 Docker/私有部署影响。**编译通过 ≠ 完成。**

### 3.9 可靠性 / AI 模型独立

不把核心业务安全建立在某个 LLM 的合规上。运行时必须**独立于模型输出**强制执行关键控制。LLM 输出是不可信输入。提示词可改善行为，但权限/确认/治理/校验/审计必须由确定性的应用/运行时机制强制。

### 3.10 性能与部署

只在影响用户体验或生产可靠性时优化性能，用可测证据。不为理论规模引入复杂缓存/队列/分布式/微服务，单进程/简单部署足够就不做。保住 KeelBase 的部署优势：Docker、单容器 demo/部署、离线/私有部署、本地模型支持。新特性不无谓增加私有部署难度。

### 3.11 单开发者约束

默认假设约**一名全职核心开发者 + AI 辅助**。因此：优先复用而非新子系统；一条强工作流胜过多条浅工作流；Web 是主产品工作台（除非需求证明否则）；控制 Flutter/Taro/移动范围；不平行扩展多个模型供应商；不做大规模平台重写；P0 工作保持少量并发轨道。小垂直切片、增量改动、既有依赖、显式模块边界、低运维负担、文档随实现生成。容量模型：**60% 核心产品/旗舰 / 20% 稳定性·测试·架构·债 / 10% 社区与开发体验 / 10% 探索**。

## 4. 开发流程与执行（融合市场最佳实践）

> 本节补齐原三篇缺失的执行闭环。参照 Anthropic 官方（spec-driven / tdd / code-review）与 mattpocock skills（implement→to-spec→to-tickets→code-review 编排 + 完成定义）。

### 4.1 开发生命周期

对非平凡工作，按此顺序走，每步有明确产出：

1. **Spec / 计划**：写清问题、JTBD、范围、验收、明确非目标 → 产出简短 spec（`docs/*.spec.md` 或 ADR）。复杂需求先做需求确认（`docs/*-requirements.md`，见 CLAUDE.md §11.3）。
2. **拆票**（可选，工作较大时）：拆成有边界的增量，每张声明阻塞关系与验收（对齐 `to-tickets`/`wayfinder` 思路）。
3. **实现最小闭环**：按 §4.2 评估后，实现能证明价值的最小方案。小步、垂直切片、随改随测。
4. **测试**：按 §3.7 补测试；AI 工具/权限/治理路径允许与拒绝都测。
5. **评审**：按 §4.4 三方评审后整合（阻塞项必修、建议项择优）。
6. **收尾**：回归纪律（§3.8）+ DoD（§4.3）+ 文档/端点同步（CLAUDE.md §11.2）+ 迁移一致性 + 提交纪律。

### 4.2 开发前必答（非平凡改动，动手前先在答复中给出）

统一模板（合并原三篇的评审格式，去重）：

1. 用户类型：Builder / End User / Both
2. 问题 / JTBD（具体痛点）
3. 产品价值 + 优先级依据（§1.3 八维 / §1.4 决策）
4. MVP 范围
5. UX 影响（§2.2 原则 + 接受状态 §2.4）
6. 信任/安全影响（§1.7 / §3.3 + 项目安全红线）
7. 复用的现有能力（§3.2 清单）+ 架构影响（§3）
8. 数据模型 / API / 迁移影响
9. 测试计划（§3.7）+ 回归面（§3.8）
10. 部署影响（§3.10）+ 回滚/恢复
11. 可测量验收指标
12. **明确非目标**

答不清则先澄清再实现。实现最小安全改动。

### 4.3 完成定义（Definition of Done）

一个改动在声称完成前必须：

- [ ] 走通目标用户流（Builder 与/或 End User），失败路径不混乱
- [ ] 安全/治理未削弱：权限、确认、审计、敏感脱敏未破坏（对照 CLAUDE.md §5 安全规则 + §5.5 红线）
- [ ] 测试就位且通过：聚焦测试 + 影响面的回归；AI 工具允许/拒绝两路径
- [ ] 迁移一致：`migration:generate` 输出 "No changes"（新实体/改列后必跑）
- [ ] 模块接线完整：`app.module` / `modules-manifest` / AI 导航（`navigate-page.tool`）等按 AGENTS.md 清单
- [ ] 双语齐全（管理端 `src/i18n/`；App `app_localizations`），无硬编码中文
- [ ] 文档同步：新 API/字段/规则/环境变量已更新对应 spec 与 CLAUDE.md §9 端点表（§11.2）
- [ ] 构建通过：后端 `npm run build` + 前端 typecheck / `flutter analyze` 0 error
- [ ] 未意外扩大范围

### 4.4 评审流程（三方评审）

每次发布前与重要改动后，对本次 diff 跑**三方评审**后汇总整合（详见 `docs/manual/release-precheck.md`）：

1. **阿里 OpenCodeReview**：`ocr review --from <base> --to <head>` 或会话内 `/open-code-review:delegate-review`
2. **Claude 自带 code review**：多维（正确性/安全/性能/简化/测试覆盖）
3. **code-review skill**（mattpocock）：`/code-review <commit|branch|tag>`，双轴 Standards/Spec

整合三份结果：去重、分级（阻塞/建议/风格），**阻塞项必须修复**，建议项择优落地，改进并入。

### 4.5 项目执行约定

- **git 纪律**：工作时间（工作日 05:00–19:00 北京时间）只提交不推送；提交后 `git log -1 --format='%h %ad'` 验证映射；推送前检查时间并获用户明确授权；rebase/amend/cherry-pick 后同时查 author 与 committer 两个时间。
- **提交前审计**：commit 前 `git status` + `git diff` 自查 + 相关测试 + 安全面审查。
- **隐私**：管理端接口 `sanitizeForAdmin` 脱敏；审计 `requestBody` 敏感字段打码；App 本人路径可明文。
- **双语**：所有用户可见文案走 i18n（App `app_localizations` 中英 / 管理端 `src/i18n/` 中英）。
- **审计**：操作审计/AI 审计联用户表带 `username` + `feature-map` 语义功能名。
- **提交消息**：中英双语（`类型: 英文 — 中文`），不带 Co-Authored-By。

### 4.6 容量与优先级

P0 少量并发轨道；容量 60/20/10/10（§3.11）。优先级默认：P0 直接证明产品价值/Trust Runtime 差异化/关键体验；P1 强支撑采用/集成/产品化；P2 有用可等证据；P3 后置；P4 暂避。优先满足下列至少两条的工作：改善首价值时长、改善首次可信应用时长、提升真实业务任务完成、提升业务安全、支持外部系统集成、改善 Builder DX、改善 End User UX、强化可复用方案模板、提供可测 PMF 证据。

## 5. 决策规则

### 5.1 最终优先级链

产品优先级冲突时按序裁决：

`真实客户价值 > 终端用户可用性 > Builder 可用性 > 业务安全 > PMF 证据 > 可复用性 > 技术优雅 > 功能广度`

### 5.2 两难时的选择

两个技术上都有效的实现之间，选那个：

> 让产品对首次用户**更容易理解**、对开发者**更容易构建**、对业务**更安全可信任**、对将来客户项目**更容易复用**。

不因视觉新颖而伤害可用性（UX）；不因架构复杂而没有具体的产品或运维理由（工程）。
