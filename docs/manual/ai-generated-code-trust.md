# AI 生成的代码，凭什么信任？/ Why Trust AI-Generated Code?

> 一篇面向技术团队的技术文章（社区 / 发布草稿）。讨论一个现实问题：当代码越来越多由 AI 生成，团队靠什么信任它？答案是工程哲学——**默认不信任，强制可溯源，验证才放行**。
> A technical article for engineering teams (community / publication draft). A practical question: as more code is written by AI, what makes it trustworthy? The answer is an engineering discipline — **untrusted by default, traceable by provenance, released only after verification**.

---

## 现实：AI 写的代码，正在成为默认

越来越多团队用 AI 生成业务模块、CRUD、测试、甚至整个应用的骨架。效率提升是真实的。但出现了一个新的、微妙的信任转移：

> **以前**：代码是"人写的，人可以解释"——信任建立在作者身上。
> **现在**：代码是"AI 写的，没人完全读过每一行"——信任建立在……什么上？

如果答案是"AI 很聪明，所以信它"，那团队已经把信任交给了它无法解释的东西。更糟的是：AI 代码的 bug 往往藏在"看起来对"的地方——权限检查漏了、边界没处理、校验被跳过。这些错误不是语法错误，是**语义边界**的错误，编译器不报，测试不查，上线才炸。

## 三种风险：不知道来源、没被验证、无法追踪

AI 生成代码带来三类具体风险：

1. **来源不明**：这段代码是 AI 从哪个协议 / 需求生成的？用了什么假设？如果 AI 基于错误的业务理解生成了代码，没人知道它"以为"了什么。
2. **未被验证**：AI 生成的代码过了哪些检查？编译通过 ≠ 逻辑正确 ≠ 安全。如果只有"能编译"就上生产，边界问题必然漏网。
3. **无法追踪**：出问题后，能否知道"这是 AI 生成的哪部分，当初基于什么生成"？如果代码和人写的混在一起，事后无法溯源。

## 解法：把"信任 AI"改成"让 AI 的产出可验证"

思路不是"禁止 AI 写代码"（那不现实），而是**改变信任的来源**——从"信任 AI 的判断"改为"信任验证链的结果"：

```
AI 生成 → 记录来源（provenance）→ 架构约束 → 静态检查
       → 单元测试 → 集成测试 → 安全测试 → E2E → 评审 → 上线
```

关键区别：**AI 生成 ≠ 自动信任**。每一步验证是放行条件，不是可选项。

### 1. 来源可溯源（Provenance）

AI 生成代码时，记录它的"出生证明"：由哪个协议 / 需求 / 提示生成、生成器版本、生成时刻、通过了哪些检查。

- 好处：任何一段 AI 代码，都能回答"它从哪来、基于什么、是什么版本生成的"。
- 反例：手写代码没有 provenance 可以接受（作者负责）；AI 代码没有 provenance 就是**匿名代码**——出了问题不知道找谁，不知道当初的意图。

### 2. 验证是硬门槛，不是软建议

编译、单元测试、集成测试、安全测试、E2E、性能基准——每一项都是"未通过即不放行"的门槛，而不是"尽量跑一下"。

- 尤其针对 AI 代码：AI 容易在"语义边界"犯错（权限、校验、数据范围）。这些要有**专门的边界测试**，不是靠代码评审人肉找。
- 一个实用的做法：给 AI 生成的代码配"越权测试""注入测试""边界测试"——用运行时验证，而不是依赖 review 时"看出来"。

### 3. 评审仍然存在，但更聚焦

AI 代码的评审不必逐行读（那会失去 AI 的意义），而是聚焦：
- 边界是否由运行时强制（不是靠注释 / 提示词）
- 授权是否与能力分离
- 是否有可运行的验证
- 重要动作是否可恢复

## 一个实践：KeelBase 怎么做

作为参考实现，KeelBase 把这条原则落进了生成器：

- **生成即记录来源**：`keelbase init` 生成每个模块时，自动写 `.keelbase-provenance.json`（来源 spec / 生成器版本 / 协议 / 生成时刻）——每段 AI 生成代码都有出生证明。
- **溯源可视化**：`keelbase inspect` 展示各模块的来源与生成时间，回答"这段代码哪来的"。
- **验证链成体系**：生成器自带单测、迁移、AI 工具测试；CI 有全量测试门禁 + 代码评审（Code Economy Review：查重复 / 过度抽象 / 不必要的复杂度）。
- **哲学层面**：KeelBase 把这条写进了工程 DNA——"AI-generated code is untrusted by default"，与运行时对待 Agent 的方式一致（Agent 行为默认不被信任，靠运行时治理）。

## 给你的行动清单

1. **建立 provenance**：AI 生成的代码，强制记录来源（协议 / 提示 / 生成器版本 / 时刻）。没有来源的 AI 代码不进仓库。
2. **验证是门槛**：AI 代码至少过编译 + 单测 + 边界测试，未通过不放行。
3. **边界专项测试**：AI 生成的 CRUD / 工具，专门补越权、注入、数据范围测试——这是 AI 代码最常漏的地方。
4. **出问题能溯源**：能回答"这段代码哪来的、基于什么生成、过了哪些检查"。

> **一句话**：AI 生成代码的价值是效率，不是信任。信任只能来自验证链——默认不信任，验证才放行。
