# 全量 e2e 硬崩 `0xC0000409` 的根因与对照读数（2026-11-11）

> **结论**：这是**本机 node 24.15.0 的上游缺陷**，不是本仓代码的红。
> 对应 [nodejs/node#62260](https://github.com/nodejs/node/issues/62260)（**OPEN**，label `v8 engine`，*V8 Maglev JIT causes STATUS_STACK_BUFFER_OVERRUN (0xC0000409) on Windows*）。
> 同一负载下 **node 24.15.0 崩 7/16 次、node 24.22.2 崩 0/16 次**（逐轮交错）；抬到 24.22.2 后整轮 `npm run test:e2e` 为 `44 suites / 439 tests` 全过、`EXIT=0`、崩溃重试分支一次未触发。

## 1. 环境

| 项 | 读数 |
|---|---|
| 运行时（崩溃发生时） | node **v24.15.0** / V8 **13.6.233.17-node.48** / libuv **1.51.0** / modules 137 / x64 |
| 系统 | Windows 11 build **10.0.26300.9974** |
| 空闲内存 | 崩时 **14.7 GB / 32 GB**（同日上午另一次崩溃时约 2.0 GB） |
| 安全软件 | 仅 Windows Defender（实时保护开启） |
| 跑法 | `cd Server-NestJS && npm run test:e2e` → `scripts/run-e2e-shards.mjs`（jest `--shard=N/4`，每片最多 3 次，只对「无 `Test Suites:` 汇总行」重试） |

## 2. 复现读数

一轮全量，两片各崩一次、重试即绿：

| 片 | 尝试 | 结果 | 耗时 | 崩溃前跑完的套件 |
|---|---|---|---|---|
| 1/4 · 2/4 | 1 | 绿 | — | 11 / 115、11 / 58 |
| **3/4** | 1 | **崩 `3221226505`** | **11.8 s** | **0 个**（死在第一个套件之内） |
| 3/4 | 2 | 绿 | — | 11 / 206 |
| **4/4** | 1 | **崩 `3221226505`** | **18.0 s** | 6 个 |
| 4/4 | 2 | 绿 | — | 11 / 60 |
| 整体 | — | **EXIT=0** | — | 44 / 439 |

崩溃时空闲内存 **14.7 GB** ⇒ **低内存不是触发条件**。崩溃末段全是正常的 401/403/404 业务日志，**没有一条 `FAIL`**、没有 JS 栈、没有 jest 汇总行。

## 3. 与上游缺陷的签名比对

| 判据 | #62260 报告 | 本机实测 |
|---|---|---|
| 退出码 | `-1073740791` = `0xC0000409` | `3221226505` = `0xC0000409` |
| node / V8 / libuv | 24.15.0 / 13.6.233.17-node.48 / 1.51.0 | **逐项相同** |
| 系统 | Windows 11 build **26200** 线 | Windows 11 build **26300**.9974（同代） |
| 输出 | 零 JS 栈、无 stderr、**无 WER 事件**（`__fastfail` 绕过） | 崩溃前后 Application 日志**无 1000/1001/1026** |
| 位置 | "the affected file **moves around**" | 四片都中过；崩溃前跑完 0–10 个套件不等 |
| 复跑 | 重试即过 | 两次崩溃重试均绿 |
| 触发形状 | 多模块 import 图 + 每例起临时端口 HTTP 服务并回环 `fetch` | 42/44 个 e2e 文件走 `app.getHttpServer()`（超测 → 每例回环连接） |

> 该单另有 2026-08-05 一条实证：node **24.19.0** 与 **22.23.2** 在同一负载下不再崩、24.12.0 崩 5/5 ⇒ **24.15.0 落在已知坏窗口内**。

## 4. 决定性对照：换 node 版本

同一目标（`test/app.e2e-spec.ts`，单套件）、同一 cwd、同一 `--forceExit`，**两臂逐轮交错**（A/B/A/B…）以抵消机器状态漂移；每臂 **n=16**。两臂共用同一 `node_modules`（modules 137 未变），唯一变量是 node 二进制。

| 臂 | 绿 | 崩 `0xC0000409` | 红 |
|---|---|---|---|
| **node 24.15.0** | 9 | **7** | 0 |
| **node 24.22.2** | **16** | **0** | 0 |

- Fisher 精确检验（双尾）**p ≈ 6.8 × 10⁻³**；效应量 **7 : 0**。
- 24.15 的 7 次崩全部落在 **12.0–14.3 s**、**7 次都 0 个套件跑完**（连一条 `PASS`/`FAIL` 都没有）；同臂跑绿平均 21.8 s ⇒ 稳定死在套件跑完之前，不是收尾时。
- 24.22.2 的 16 次耗时 19.7–23.3 s，无一次异常。
- 全程空闲内存 4.2–7.1 GB ⇒ 这一组差异不能用内存解释。

### 4.1 参数对照（同一 node 24.15，三臂交错，各 n=8）

| 臂 | 绿 | 崩 |
|---|---|---|
| 无旗标 | 7 | 1 |
| `--no-maglev` | **8** | **0** |
| `--max-old-space-size=384` | 3 | **5** |

- `--no-maglev` 0/8 与上游"只降不消"的方向一致，但**样本不足以下结论**（与 §4 的对照基线合并为 8/24，Fisher 双尾 p ≈ 0.13）。
- **堆参数不是解法**：把老年代压到 384 MB 后崩得更多（5/8，其中一次 6.1 s）。这与 2026-10-31 `--max-semi-space-size=64` 无效的结论一致。
- 崩溃率对时间/机器状态敏感（同一基线臂在不同窗口为 7/16 与 1/8）⇒ 任何 A/B 必须逐轮交错；"某次跑绿了"不能当证据。

### 4.2 换装后的整轮复验

`npm run test:e2e`（真实入口）在 node 24.22.2 上：四片各 **11 suites**，合计 **44 suites / 439 tests（115 + 58 + 206 + 60）全过**，**`EXIT=0`**，**崩溃重试分支一次未触发**。

## 5. 已排除 / 保留

**排除**

| 假设 | 判据 |
|---|---|
| jest worker 子进程 | `test/jest-e2e.json` 的 `maxWorkers: 1` 使 jest 29.7 的 `shouldRunInBand()` 直接返回 `true`（in-band），跑批期进程表只有一个 jest；`--runInBand` 是空操作 |
| 低内存 / OOM | 14.7 GB 空闲下仍崩；崩前无 `0xC0000005`、无 V8 heap OOM 报错 |
| 第三方 Winsock LSP | `netsh winsock show catalog`：28 条提供程序路径全是 `%SystemRoot%\system32\mswsock.dll`，无第三方条目 |
| JS 堆 / GC 压力 | `--max-old-space-size=384` 反而更差；`--max-semi-space-size=64` 曾使转储读数完全一致 |
| 第三方原生插件在故障栈 | 三份转储的故障地址与栈全在 `node.exe` 内；skia / libvips / better_sqlite3 / bcrypt 只是被加载 |

**保留（来自 2026-10-31 的三份进程转储）**

- 异常码 `0xC0000409`，参数 `[2]` = `FAST_FAIL_STACK_COOKIE_CHECK_FAILURE`，地址 `node.exe+0x21F2189` = `__report_gsfailure+0x1D`；
- 故障栈：`__report_gsfailure` ← **`uv__tcp_connect+0x3AF`**（`uv__tcp_try_connect` 内联），崩溃时正在连 `127.0.0.1`；
- 整条栈只有这一帧的 `/GS` Cookie 对不上，被写入的值恒为 `0x0001030000000000`（两次不同进程的 `__security_cookie` 不同、写入值相同 ⇒ 确定性写入）。

结合本轮的上游对齐，`uv__tcp_connect` **是被踩到的受害者帧，不是肇事者**——这解释了"故障点恒在同一处、崩溃位置却在分片间漂移"。

## 6. 版本落点

| 位置 | 版本 |
|---|---|
| 本机开发环境 | 原 **24.15.0**（坏窗口内）→ 2026-11-11 已抬到 **24.22.2** |
| GitHub Actions CI | **22**（`ci.yml` `env: NODE_VERSION: '22'`，ubuntu runner） |
| Docker 运行镜像 | **node:22-alpine**（按 digest 固定） |
| `engines.node`（根与 `Server-NestJS`） | `>=22` |

⇒ CI 与产线镜像都在 22 上、且跑在 Linux，不在本缺陷已报告的 Windows 影响面内（未在 CI/Linux 上验证）。若要回到与 CI 完全一致，需在 node 22 下重建原生插件（ABI 127 与本机现场编译的 137 不兼容）。
