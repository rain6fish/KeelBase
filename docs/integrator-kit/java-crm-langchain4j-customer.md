## 1. 背景与目标 / Background & Objectives

贵司拥有一套在生产的**存量 Java CRM**（Spring Boot + 自有数据库，不作替换），并已基于 **LangChain4j** 构建了「客户推荐 / 跟进提醒」AI Agent，用于辅助销售决策。

本方案在不替换上述任一技术栈的前提下，为贵司的 AI 业务使用加一层**可治理**能力，解决四件事：

| # | 要解决的事 | 对应价值 |
|---|---|---|
| 1 | **看得见** | 每一笔 AI 调用（谁问的、什么模型、多少 tokens、耗时）都可查、可回溯、可计成本 |
| 2 | **管得住** | AI 读数据按"这个人是销售/主管、只读得到自己该读的客户"来授权；AI 写数据必须人工确认后才执行 |
| 3 | **可撤销** | AI 创建的跟进任务、状态变更等，事后可一键撤销、且撤销本身留痕 |
| 4 | **留证据** | 全程审计写入不可篡改的哈希链，可离线导出，供内部合规与审计复核 |

> 一句话：**给"老 CRM + 现成 Agent"加一层 AI 治理，不迁移、不重写、不上云。**
> In one sentence: add a governance layer over your legacy CRM + existing agent — no migration, no rewrite, no cloud.

## 2. 方案架构（一页） / Solution Architecture (One Page)

`存量 Java CRM` 仍是**数据面**（业务数据永不出域）；`LangChain4j Agent` 仍是贵司自有的**编排者**；`KeelBase 治理平台` 作为**治理面**旁挂，只回答"谁的身份 / 能不能 / 要不要确认 / 做了什么 / 可否撤销"，不触碰 CRM 数据库。

```text
                           客户现有环境（不动）
┌──────────────────────────  legacy Java CRM  ──────────────────────────┐
│                                                                        │
│   CRM 业务库(客户/订单/跟进/任务)  ◄──── 数据永远留在 CRM ────────────┤
│        ▲                                        ▲                      │
│        │ 现有 REST                               │ 需开放的 AI 读/写端点 │
│   ┌────┴───────────────┐                  ┌──────┴─────────────┐        │
│   │ LangChain4j 推荐    │                  │ Java 接入组件       │        │
│   │ Agent(继续编排,客户 │                  │ (委托验签/工具导出/ │        │
│   │ 自持,不替换)        │                  │  撤销补偿)          │        │
│   └────┬───────────────┘                  └──────────▲─────────┘        │
│        │ LLM 调用(OpenAI 兼容)                        │ 委托身份(带目标系统 │
└────────┼──────────────────────────────────────────────┤ audience,短时效)──┘
         ▼ base_url 指向治理旁路                          │
   ┌────────── AI 治理旁路 :3200 ──────────┐              │
   │ 旁路审计每一笔 AI 调用                  │              ▼
   │ 工具门控: 高风险阻断/写需确认/读放行    │     ┌────────── KeelBase 治理平台 ──────────┐
   └─────────────────┬─────────────────────┘     │ 代理工具(读自动/写人工确认后执行)        │
                     │ 服务身份上报                │ AI 审计哈希链 · 策略 · 副作用 · 撤销路由 │
                     ▼                            │ 对话/记忆/评测(可按需启用)               │
   ┌────────── 治理控制台(集中审计) ─────────┐   └──────────────────────────────────────────┘
   │ 统一审计视图: N 个业务系统同一张账        │   管理/审计界面 = KeelBase 管理控制台
   │ 策略下发 · 撤销发起                      │   AI 使用入口 = 工作台 / CRM 现有入口
   └──────────────────────────────────────────┘
```

**三条约定的数据流（对客户讲清）**

| 流向 | 路径 | 治理效果 |
|---|---|---|
| ① AI 对话流量 | Agent → 治理旁路 → 大模型 | 每笔对话入审计（旁路透明，Agent 无需改业务逻辑） |
| ② 业务读 | Agent 取数 → KeelBase 代理工具 → CRM REST | 只读得到该用户有权读的客户；越权读取被拒并留痕 |
| ③ 业务写（可选阶段） | 用户确认 → KeelBase 执行 → CRM REST；撤销 → CRM 补偿端点 | 写不确认不执行；事后可撤销、撤销幂等 |

## 3. 接入内容与边界 / Scope & Out of Scope

**需要贵司配合提供 / Customer provides**
- 一套两边一致的**用户目录/身份映射**（同一登录源或映射表）——这是"AI 以谁的身份"的前提；
- CRM 中拟开放给 AI 的**接口清单 + 读/写性质**（含金额/删除等高风险写要单独标注）；
- 网络可达（CRM ↔ KeelBase 治理平台）。

**方案明确不做 / Deliberately out of scope**
- 不迁移、不重建 CRM 数据库；不重写、不替换 LangChain4j Agent；不改变 CRM 既有 UI；
- 不引入第二套账号体系；不把业务逻辑改成"低代码/无代码生成"形态；
- AI 写操作默认按风险分级：读自动放行、业务写需人工确认、高风险写（如改金额/删除/审批）可配双人审批或直接阻断。

## 4. 分阶段实施计划 / Phased Rollout Plan

> 每阶段独立交付价值，可按需随时收尾，不必一次上全量。
> Each phase delivers standalone value; you may stop after any phase.

| 阶段 | 目标 | 客户侧改动 | 验收口径（怎么看成功） | 投入参考 |
|---|---|---|---|---|
| **P1 治理叠加**（第 1 周） | 每一笔 Agent 对话可见、可审计 | Agent 的大模型地址指向治理旁路（约 1 行配置） | 治理控制台能看到贵司 Agent 的逐笔调用（含摘要/模型/耗时）；审计链校验通过 | 客户约半天 |
| **P2 有权读**（第 2–3 周） | 推荐结论基于"该用户有权读"的真实客户数据，读取全程留痕 | CRM 把 Agent 需要的读接口开放并声明为 AI 读工具（读自动放行）；Agent 取数改走 KeelBase | AI 取数返回本人/角色范围内的客户；越权（他人数据）被拒且有审计记录 | 客户约 2–3 人日 |
| **P3 写=确认+可撤销**（第 3–4 周） | AI 建跟进任务/改状态等，确认后执行、可撤销 | CRM 写接口声明为写工具 + 提供撤销补偿端点（幂等）；Agent 侧加约几十行的"确认回调"小模块 | 未确认的写不执行；确认后 CRM 收到以该用户身份发起的写入；管理台可见副作用并成功撤销、重复撤销不报错 | 客户约 3–5 人日 |
| **P4 扩展（可选）** | 多个系统一张审计账；结论接地内部文档；交付合规证据 | 视范围另议 | 多系统同一治理视图；内部资料（话术/政策）供 AI 检索引用；导出可离线复核的审计证据包 | 按范围评估 |

**时间线示意（约 4 周 PoC）**
```text
W1 ── P1 治理叠加（审计可见）──────────────▶ 可独立验收点
W2 ── P2 有权读 + 结论落地真实数据 ────────▶ 可独立验收点
W3 ── P3 写确认 + 撤销闭环 ────────────────▶
W4 ── 复盘 + P4 扩展决策 ─────────────────▶ Go/No-Go
```

**成功指标（建议双方对齐）**
| 指标 | 目标 |
|---|---|
| AI 调用审计覆盖率 | 100%（逐笔可查：调用人/模型/tokens/耗时） |
| AI 写操作 | 100% 有"确认→执行→审计"，撤销演练至少通过 1 次 |
| 越权/跨用户读取 | 0（被拒且留痕） |
| 业务效果（推荐采纳率、复核工时等） | 以贵司基线为准，PoC 记录前后对比 |

## 5. 风险与注意事项（诚实说明） / Notes & Caveats

- **身份目录需先对齐**：两边用户映射不一致会直接导致授权判断为空，须在 P1 前确认；
- **写操作的确认体验**：AI 发起写操作时需要一个"确认/拒绝"的交互点；若走贵司现有 Agent 界面，需在 Agent 内加一个小的确认回调模块（P3 阶段，约几十行）；
- **审计证据链 ≠ 业务事实**：技术保证"审计不被篡改"，"谁批准了什么"取决于确认记录本身，实施时会把确认与副作用一并归档成证据包；
- 默认采用**私有化部署**（贵司自有环境或内网），不上公有云；数据与密钥均不出贵司环境。
